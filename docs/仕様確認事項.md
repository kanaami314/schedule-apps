## ✅ 解決済みの論点

### C-1. 累積負荷計算の「予定時間」の単位 → **時間単位で確定**
会話で明示（「時間は時間単位で計算します」）。検証例：低負荷1.5×4時間＝6.0／中負荷2.0×3時間＝6.0／高負荷3.0×2時間＝6.0。
→ `累積負荷量 = 単位負荷量 × 予定時間(h)`。分は 60 で割る。休憩・回復の「◯分」区分はそのまま分で判定。

### C-4. 休憩自動配置のタイミングと挿入位置 → **確定**
- **判定**: 予定を時系列に走査し、休憩を挟まず連続する予定の累積負荷量を加算した「連続負荷量」を追跡。**総合累積負荷が 6.0 以上で高負荷連続と判定し休憩を自動配置**、8.0 以上でより長い休憩。
- **休憩長**: 6.0〜8.0未満＝15分、8.0以上＝30分（空きが足りなければ確保できる最大、5分未満なら配置しない）。
- **挿入位置の優先順**: 高負荷予定の「間」→「直後」→「直前」。後続の柔軟なタスクを後ろへずらして挿入。後続が固定予定なら間に入れられないため、固定予定の前／後で確保、無理なら警告。
- **空き時間による連続負荷量の増減**（§13と整合）: 5分未満=変化なし／5〜14分=25%減／15〜29分=50%減／30分以上=0リセット（純粋な空き時間の場合）。

### C-5. 自由活動の負荷計算 → **確定（配分・順序・二重構造すべて）**
- `効果量 = 強度(1〜3) × 活動時間(h) × 0.5`（効果係数0.5は暫定パラメータ、将来調整可）。消耗量も同式（消耗係数0.5）。
- **配分の解釈**: §6.4 の割合は効果量を集中／精神へ振り分ける比率。会話で確認（気分転換＝集中50%/精神50% など）。
- **適用順序**: 軸ごとに `活動後 = max(0, 活動前 + 消耗量 − 回復量)`。
- **絶対量と割合の二重構造は意図的**: 自由活動は効果量（絶対量）で増減、回復区間(§13)は割合(%)で減少。累積負荷は絶対値の running value として保持すれば整合。
- **身体負荷は回復しない**（回復5効果に身体回復がないため）。消耗（身体的に疲れる）のみ加算。身体負荷の回復は休憩・睡眠・食事・入浴・未配置区間が担う。
- **75%上限（§6.7）は仕様書のみの追加ルール**（会話は floor 0 のみ）。仕様書優先で「開始前累積負荷の75%を上限」を採用。回復区間(§13)側に上限がない非対称は意図的。

### C-5b. 自由活動の登録項目・自動配置 → **確定（2026-08-04, 会話ログの8項目を採用）**
仕様書 §6 は登録項目を「活動名/カテゴリ/活動時間/場所/効果」としか書かず、**いつ・どのくらい・自動配置するか**が抜けていた（§3 は自由活動を配置順4番目と規定）。設計会話ログ「初回登録時に本当に入力させる項目」に基づき、次の8項目を必須の登録項目とする:
1. 活動名 2. カテゴリ 3. 最短実行時間 4. 希望実行時間 5. 希望頻度（週N回等）6. 実行可能な曜日・時間帯 7. 分割可能か 8. 自動配置するか
- **自動配置**: 自動配置オンかつ実行可能曜日に該当する日、実行可能時間帯の残り空きへ希望実行時間ぶん配置（入らなければ最短実行時間まで短縮）。§3の4番目、休憩確保では最初に後方移動（movable）。
- **希望頻度（週N回）**: 週単位の回数上限の**厳密遵守は複数日対応で完成**。現状は値として保持し、単日では「実行可能日に空きがあれば置く」まで。
- 効果（回復/消耗）は §6/C-5 の負荷計算にそのまま使用。

### C-6. 回復区間の連続適用・予定未配置区間の自動回復 → **確定**
- **逐次適用**: 各回復区間ごとに `L_after = max(0, L_before − R)`、R は種類×継続時間で決まる割合。連続する回復区間は順に掛け合わせる（会話の食事→就活の例で確認）。
- **予定未配置区間も自動回復**。休憩より回復率が低いのは「本当に休んでいるとは限らない」ため（意図的）。
- **回復除外**: 移動・準備・終了後余裕・他予定に拘束された時間・家事・中/高負荷の自由活動は回復区間に含めない。「純粋な未配置区間」のみ回復。

### C-2. 累積負荷の起点・リセット → **実質確定（イベント駆動）**
明示的な「日付境界リセット」は設けず、**回復区間によるリセットで管理**する。
- 睡眠2時間以上＝完全リセット、未配置60分以上＝完全リセット、30分以上の空き＝0リセット。
- 睡眠(生活ルーチン)を挟むことで各日は実質 0 から始まる。連続負荷量は「直前の完全リセット以降の累積」。
- （軽微な残点：睡眠が記録されない日の扱いのみ後述 → 🔵M-6）

### I-6. §5.5「分割しにくい」「短い」の定量化 → **確定**
配置順のタイブレークは以下（会話で明示）:
1. 分割不可のタスク
2. 分割可だが**最短作業時間が長い**タスク
3. 分割可で最短作業時間が短いタスク
→ さらに同条件なら**所要時間が短い順**、最後に**登録が古い順**。

### 自動分割 → **確定**
分割可能な柔軟なタスクは**アプリが自動分割**する（固定予定は分割しない）。各枠は最短作業時間を下回らない。空き時間や休憩基準（総合累積負荷が閾値を超えないよう）に合わせて分割する。

### I-1. 休憩確保／生活ルーチン確保のための予定移動先 → **確定**
移動対象（自由活動・柔軟なタスク）は**同日内で後ろへずらして再配置**。固定予定は移動しない。生活ルーチン確保のためなら柔軟なタスク・自由活動を移動・再配置してよい。

### I-2. 生活ルーチンの移動 → **確定**
生活ルーチンは固定予定の次の優先度。休憩確保のためには移動しない（例外なし）。必要時間を確保できなければ短縮せず未配置。

### I-4. 生活ルーチンの複数回配置 → **確定**
均等分割ではなく、**各回ごとに「実行可能時間帯」と「必要時間」を個別設定**（例: 食事1回目 06:00-10:00/30分、2回目 11:00-15:00/45分…）。各時間帯の中で、予定状況に応じて開始時刻を変えて配置。既存予定（会食など）が兼ねている場合は自動配置しない。

### I-5. §5.4 関連固定予定の実行条件で配置不能 → **確定**
いずれの条件でも配置できなければ、§16.6「関連固定予定の条件を満たせない」として未配置＋通知。

### C-3. 「期限」と「優先度」の合成方法 → **確定（辞書式）**
配置フロー第一段階「期限・優先度を評価」を、**辞書式（段階比較）** で確定。合成スコアではなく、上位キーから順に比較し同点なら次のキーへ進む。

**前提の値域**:
- 優先度（§5.1 必須）: 高 / 中 / 低
- 期限の厳しさ（§5.2 任意）: 厳守 / できれば守る / 目安。**未設定時は「できれば守る」**（中央）。
- 〆切間近しきい値 D: ユーザー設定可、**既定3日**（§15.1）。
- 基準時刻: 再スケジューリングを実行する時点。残り時間 `R = 期限 − 基準時刻`。

**第一段階のキー順（上位から比較）**:

| 順位 | キー | 内容 |
|---|---|---|
| ① | **締切区分** | `0: 期限超過・当日` / `1: 〆切間近(R≤D)` / `2: 通常(R>D)` — 番号が小さいほど先 |
| ② | **優先度** | 高 > 中 > 低 |
| ③ | **期限の厳しさ** | 厳守 > できれば守る > 目安 |
| ④ | **残り時間 R** | 小さい順（期限が早い順） |

→ ここまでで完全順序が決まり、以降は確定済みフロー（関連固定予定で配置可能期間を限定 → 分割しにくい順(I-6) → 短い順 → 登録が古い順）へ続く。

**設計意図**: まず締切の近さで大きく分け（締切超過を最優先で回避）、同程度の締切内で優先度→厳しさ→期限順に効かせる。締切区分を優先度より先に見ることをユーザー確認済み。

## 🔵 軽微な残点

### I-3. カテゴリ階層(最大3階層)での負荷継承の遡り方
継承順は「個別設定 → カテゴリ設定 → 初期値"普通"」で確定。ただし**カテゴリ設定を子→親→祖先へ遡って探すか**、割り当てカテゴリ自身のみ見るかは未明示。
**推奨案**: 割り当てカテゴリから最上位へ遡り、最初に見つかった設定を採用。なければ"普通"。（色分けは §8.4 で最上位カテゴリ基準と確定済み。負荷継承の遡りも同様に扱うのが自然）

### M-2. 未完了申告の有効期限（§14.3）
「後から未完了申告」を受け付ける期限が未定義。**推奨案**: 当日中（日次振り返りまで）。

### M-3. 再生成抑制の「前/後ろの予定」の同一性判定（§18.3, §18.4）
**推奨案**: 予定IDで判定。IDが変われば「組み合わせが変わった」として抑制解除。

### M-4. 通知の実現範囲（GitHub Pages 制約）
現構成ではアプリ終了中のOSプッシュ通知は困難。**推奨案**: 当面「アプリ起動中／Service Worker生存中の通知」に限定。§16 の通知ロジックはデータとして保持し、サーバー移行時に本格対応。

### M-5. 効果係数・消耗係数(0.5) の扱い
会話で「暫定的な調整係数、将来調整可能」と明言。**推奨案**: 実装では**定数だが1箇所で管理**し、後日パラメータ化しやすくする。

### M-6. 睡眠が記録されない日の累積負荷（C-2 の残点）
睡眠ルーチン未配置・未記録の日は完全リセットが発生しない可能性。**推奨案**: 暦日の境界（例: 生活ルーチンの睡眠時間帯 or 0時）でも保険的にリセット。要確認。
